# Практика 5. Junit
## Завдання
1. Створити унікальні власні тести з JUnit 6:
- простий тест
- параметризований тест з 1 параметром (параметри статичні)
- параметризований тест з набором параметрів (параметри статичні)
- тест динамічний(@TestFactory)

> Загалом має бути не менше за 4 тести.

2. Використати Assumptions, який матиме логічний сенс.

3. Використати розділення на Suite тестів(окремі набори за тегами або іншою ознакою). Показати різницю запусків різних наборів.

## Реалізація
### Контекст
Проєкт, до якого пишемо тести — реалізація алгоритму Cluster Pruning для оптимізації інформаційного пошуку. Клас ClusterPruning виконує офлайн-кластеризацію векторів документів pre-pruning за допомогою випадкового вибору лідерів та онлайн-пошук pruning, що використовує косинусну подібність для знаходження найбільш релевантних документів за запитом.

### Тести
Для перевірки коректності роботи алгоритму Cluster Pruning розробила "тестове покриття" з використанням JUnit 6.
#### Типи тестів
1. **Простий тест (@Test)** — перевіряє успішне виконання методу prePrune()
2. **Параметризований тест з одним параметром** — використовує анотацію @ValueSource для виконання pruning за кількома (заздалегідь визначеними) ідентифікаторами документів
3. **Параметризований тест з набіром параметрів** — використовує анотацію @MethodSource для передачі складних аргументів, а саме вектора запиту та очікуваного мінімального розміру результатів
4. **Динамічний тест (@TestFactory)** — генерує тестові вузли (DynamicTest) під час виконання для перевірки ізоляції та наявності результатів пошуку для динамічно сформованого списку ідентифікаторів

#### Assumptions
Механізм застосований для логічної валідації умов виконання тестів:
- **Assumptions.assumeTrue(vectors.containsKey(docId))** — скасовує виконання тесту (Skip замість Fail), якщо переданий документ відсутній у базі
- **Assumptions.assumeFalse(vectors.isEmpty())** — гарантує, що тести онлайн-запитів не будуть запущені на порожній колекції векторів

#### Розділення на Test Suites (Suite Engine)
Тести згруповані за допомогою анотацій @Tag, @Suite, @SelectClasses та @IncludeTags для демонстрації вибіркового запуску:
- **OfflineTestSuite (@Tag("offline"))** — запускає тільки тести ініціалізації бази та pre-pruning
- **OnlineTestSuite (@Tag("online"))** — об'єднує набори тестів, що імітують активні клієнтські запити та математичні обчислення косинусної подібності

#### Різниця запусків
- Якщо запустити клас ClusterPruningTest, виконаються всі 4 тести (методи).
- Якщо запустити OfflineTestSuite, система побачить фільтр @IncludeTags("offline") і запустить тільки швидку перевірку ініціалізації алгоритму Cluster Pruning (pre-pruning), ігноруючи динамічні та параметризовані тести.
> Корисно для швидких перевірок на етапі збірки (у пайплайні можна вимикати/вмикати певні теги).
- Запуск OnlineTestSuite згрупує лише ті тести, що перевіряють алгоритм косинусної подібності та пошуку лідерів (теги "online"). Тест з ідентифікатором 100 у першому параметризованому тесті буде пропущено завдяки стратегії Assumptions, що зекономить ресурси, оскільки такий документ не існує.
> Різниця запусків полягає в тому, що використання конкретного Suite дозволяє ізолювати "важкі" обчислювальні тести від швидких структурних, оптимізуючи час виконання на різних етапах збірки проєкту.

#### Запуск тестів
- `./gradlew build` (якщо Gradle сконфігурований)
- `java -jar junit-platform-console-standalone-6.1.0.jar execute --class-path out --scan-class-path`
